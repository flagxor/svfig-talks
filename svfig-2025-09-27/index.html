iCE40 Format
════════════
Layout of Config RAM is a bitmap in 4 banks:
  if (right_half)
    cram_x = bank_xoff + column_width - 1 - bit_x;
  else
    cram_x = bank_xoff + bit_x;
  if (top_half)
    cram_y = bank_yoff + (15 - bit_y);
  else
    cram_y = bank_yoff + bit_y;

How to do this?
═══════════════
 • Model as a Graph
   • Node for each wire
   • 26 x 32 x 8 x 4 in several variants
   • That's a lot of objects?
     • Only 264K main memory!
 • OO + Flyweight?

When to OO?
═══════════
 • OO is often overused
   • Objects easily have impedence mismatch
     "It is better to have 100 functions operate
      on one data structure than 10 functions
      on 10 data structures." -- Alan Perlis
   • Requires lots packing and repacking data
     • Abstractions leak
 • But...
   • Works well for polymorphic simulations
     • Applying common interface to varied data

Flyweight Design Pattern
════════════════════════
 • Design Patterns:
     Elements of Reusable
       Object-Oriented Software (1994)
   - Gang of Four:
     Erich Gamma, Richard Helm,
     Ralph Johnson, and John Vlissides
   - Higher level template for problem solving
 • Flyweight Pattern
   • Separate "intrinsic" from "extrinsic" state
   • Keep one immutable flyweight per possible "intrinsic" state
   • Pass "extrinsic" state (context) in as a parameter
   • Canonical example: One object per letter

Flyweight + ICE40 Routing
═════════════════════════
 • Intrinsic State:
   • Type of wire
   • Position within a cell
 • Extrinsic State:
   • Cell X Y
   • Selection of route
 • Observations:
   • Extrinsic state is tiny aside from route
   • Route has to be stored in CRAM bitmap
   • What if we kept mutable state in the CRAM bitmap?
   • All the state except for the route is tiny
     • Why keep a whole object on the heap?

Super Fly!
══════════
 • Store intrinsic state packed
   in a single machine word
 • Store extrinsic state
   in a global structure (CRAM bitmap)
 • Keep type as tag in that word instead of a VTable
   • Dynamic dispatch on the tag

: method& ( m cls -- a ) classes mod methods * + cells dispatch + ;
: accrued ( -- a ) 0 implementing method& ;
: method   create methods , 1 +to methods does> @ over method& @ execute ;
: implementation ( cls -- ) to implementing ;
: >min ( a -- n ) cell+ @ ;         : >max ( a -- a ) @ ;
: >below ( a -- a ) 2 cells + @ ;   : >above ( a -- a) 3 cells + @ ;
: field ( min max -- "name" )

ROUTING ALGORITHM
═════════════════
: route { src dst -- f }
  src dst = if -1 exit then
  dst .getOption { p }
  p if src p dst .optionWire recurse exit then
  dst .optionCount { n }
  n 0 ?do
    i dst .setOption
    src i dst .optionWire recurse if -1 unloop exit then
    0 dst .setOption
  loop 0
;

Status
══════
• Implemented objects for all major wire types:
    Input, Output, LocalG, Span4, Span12
• What works:
  • Can input in synthesis language
  • Routes greedily
  • Output loads in visualizer
• What doesn't works:
  • Routing fails pretty easily
    • No cross span routing
    • LUT4 inputs can be permuted
    • Backtracks only within one route
  • No IO Pins / PLLs / BRAMs / DSPs
  • No globals
  • Can't simulate in design
  • cram_write not used (but could be)
